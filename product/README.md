# Full Stick（製品版）

センサー班（`sensing/`）と PC エフェクト班（`kawashima/`）の機能を1つにまとめたもの。PC で `node server.mjs` を1つ動かし、ブラウザで1つのダッシュボードを開くだけで、スマホ3台の接続から試合、プロジェクター用の映像まで全部できる。

```
 WT9011DCL ─BLE─► スマホ A（SensorLink アプリ）─┐
 WT9011DCL ─BLE─► スマホ B（SensorLink アプリ）─┼── Wi-Fi ──► PC: node server.mjs（ポート 8000）──► ダッシュボード http://localhost:8000
                  スマホ C（ブラウザで cam.html）─┘      http と https を同じポートで受ける
```

| フォルダ | 中身 |
|---|---|
| `android/` | スマホ A・B のアプリ（`sensing/android` と同じ。Kotlin、ARCore + OpenCV のタグ検出 + WitMotion IMU） |
| `dashboard/server.mjs` | ポート 8000 ひとつで、ページ配信・スマホ A・B の中継（`/ws`、センサー班と同じ形式）・スマホ C の映像（`/cam`）・証明書を受け持つ |
| `dashboard/public/` | ダッシュボード本体（下の4画面）と、スマホ C 用の `cam.html`・`trust.html` |
| `dashboard/fake-world.mjs` | ハードなしで試すための偽スマホ A・B（フィールドと矛盾しないシミュレーター） |
| `dashboard/test.mjs` | サーバーと位置合わせ・動作判定の自己チェック |

## 動かし方

```
cd product/dashboard
npm install          # 初回だけ
npm start            # IP とポート（8000）が出る
# ブラウザで http://localhost:8000 を開く
npm run fake         # ハードなしで試す：偽のスマホ A・B（http://localhost:8000/?dummy でダミーの部屋の映像も）
npm test             # 自己チェック（サーバー・位置合わせ・ゲームのシナリオ）
npm run test:game    # ゲームのルールだけを、台本どおりのシナリオ23本で確かめる
```

初回は Windows のファイアウォールで Node を（プライベートネットワークに）許可する。許可しないとスマホからつながらない。

- **スマホ A・B**：SensorLink アプリの LAN 欄に PC の IP とポート 8000 を入れて Connect。先につないだ方が A（炎）、次が B（雷）。センサー班の中継とまったく同じ形式なので、アプリは変更なし
- **スマホ C（第三者視点カメラ）**：ブラウザで `https://<PCのIP>:8000/cam.html` を開いて「開始」。カメラはブラウザが https のページでしか使えないので、初回だけ `http://<PCのIP>:8000/trust.html` の手順で証明書を信頼させる。接続画面に両方の QR コードが出る。映像は WebRTC で届き、だめなときは JPEG に自動で切り替わる
- 証明書は `openssl` で作る（Windows は Git for Windows に入っているものを自動で探す）。見つからないときは https だけが止まり、スマホ C 以外は動く。そのときは接続画面の「映像の入力」で「この PC のカメラ」を選べる

## 画面（上のタブ、または Alt+1〜4）

1. **接続**：スマホ A・B ごとに、胸カメラが検出したタグ（画面の中の位置。A・B は映像を送らない）、受信の Hz と遅延、IMU（姿勢・角速度・加速度のグラフ、軸の向き）、ARCore の状態と軌跡、AprilTag の表。スマホ C の映像と WebRTC / JPEG の状態、映像の入力の切り替え。右側に IP・ポート・QR コード、4つの動作判定（溜め・振り・回避・ガード）と最後に出た時刻、棒の軸（IMU の +Y が先端で固定）、棒の長さ、判定の履歴
2. **3D空間**：暗い 3D に、スマホ A・B（実際の大きさの長方形、視野、軌跡、向き）、スマホ C（横向きの長方形と視野）、剣の推定位置（根元から先端）、AprilTag（実物の模様の正方形：フィールドのタグと胸のタグ）、いま見えているタグへの線（固定のタグは、スキャン前でもスマホが最初に見つけた場所と向きに出て、5 回見えたら固定。見直しても動かない。4 m より遠い見え方は数えない）、センサー班 map.js の推定（点線・比較用）。左上で表示を切り替え、右に生の数値
3. **ゲーム**：3D のアリーナで試合を見る。魔法の攻撃（炎・雷の弾、小・中・大）、溜めメーター、命中、HP、残り時間、ミニマップ。アバターは、スマホ C の映像から MediaPipe（`vision.js`、Worker で1秒に最大15回。ページが重いときは間隔を自動で2〜3倍に延ばす）が見つけた姿勢と同じ姿勢をとる（右側「カメラの姿勢をアバターに反映」で切り替え。`avatarpose.js` が骨格を床の上の3D位置に直す。人が見つからないときや未スキャンのときは、これまでの動きに戻る）。右側で試合の進行、プレイヤーごとの数と手動操作、ゲームの数値の調整、ドローン視点、攻撃の記録
4. **最終映像**：スマホ C の映像に、同じ 3D の状態（エフェクト・盾）を重ねる。プロジェクターに映すのはこの画面（「全画面」か F）。下のバーで「タグでスキャン」、視点（第三者カメラ / A の胸 / B の胸。胸の視点は 3D だけで、背景の映像はない）、小窓の 3D。「映像の認識」の4つのボタン（骨格・手・棒を表示 / 人の残像 / 二人の周りを暗く / 棒の残像）を押すと、スマホ C の映像から MediaPipe で姿勢と手を、手から伸びる細い直線として棒を見つけ（`vision.js`、Worker で1秒に最大15回）、エフェクトの下に描く（`visionfx.js`）。初回は MediaPipe の読み込みに数十秒かかり、インターネットが要る。3D が映像と合わないときのために、下のバーに「3D の左右を反転」「3D の上下を反転」（両方オンで画面の中心まわりに 180° 回る。既定は両方オン。映像そのものは変えない。ダミーの部屋と胸のスマホ視点には効かない）と、「剣の左右を逆にする」（IMU の向きが逆に回るとき。既定オン）がある

右上の「設定」（S）に、プレイヤーの位置の取り方、スキャンの設定、狙い、テストモード、音量、キー操作の一覧がある。

## 試合の流れ

1. タグ（ID 0〜3、`kawashima/print/` の PDF）を床の中心に、辺を接して大きな正方形に並べる（下の「床のタグの置き方」）。人がいない状態で、4 枚がスマホ C の映像に入るようにして「タグでスキャン」（K）。スマホ C の位置・画角が決まり、ブラウザに保存される（タグの位置は動かさない）。スキャンのボタンを押さなくても、映像が届いている間は約 2.5 秒おきに中央のタグを自動で測り直して、スマホ C の位置・画角をなめらかに合わせ続ける（失敗や精度の悪い測定は無視する。ボタンは最初の合わせ直しや、位置が大きくずれたときの手動用）
2. 各プレイヤーは立ち位置で棒を前に水平に構え、アプリの Calibrate を押す
3. 「試合開始」（3）で3秒数えて試合。デモで見せるときは「デモ試合開始」（2）を使う。ルールは同じだが、魔法は撃った瞬間に相手の胸へ狙いを決め、そのまま真っすぐ飛ぶ。振り方や棒の向きに関係なく相手へ向かうが、撃ったあとに素早く横へ動けば避けられる。試合は 60 秒で、HP が 0 になるか時間切れで終わる。時間切れなら HP が多いほうの勝ち

動作は、センサー班の判定（`actions.js`）のうち、溜めと振りの2つをゲームにつなぐ。ガードはなく、避けるには実際に体を動かして弾の通り道から外れる。

| 動作 | 判定 | ゲームでは |
|---|---|---|
| 溜め | 棒を立てて先を1周回す | 溜め始め。溜めている時間で小・中・大が決まる |
| 振り | 棒を速く振って止める | 発射。溜めていなければ小、溜めていればその時間に応じた技 |

ゲームの数値は、ゲーム画面の右側「ゲームの数値（試遊で調整）」で変えられる。変えた値はブラウザに保存される。

| 項目 | 初期値 |
|---|---|
| 小（溜めなし、または溜め 1 秒未満） | ダメージ 5、0.25 秒おきに連打できる |
| 中（溜め 1〜2.5 秒） | ダメージ 20 |
| 大（溜め 2.5 秒以上） | ダメージ 60 |
| 溜め失敗 | 棒を回すのを 1.5 秒やめる（溜めている間も歩ける。ステップや向き変えの最中は 4 秒まで待つ） |
| 玉の大きさ | 小・中・大それぞれ 1 倍。見た目と当たりの大きさが一緒に変わる（0.2〜4 倍） |

エフェクトは3組あり、ゲーム画面の右側「エフェクトを試す」で切り替える。初期値は、本番で使う「プログラム版」。

| 組 | 作り | ファイル |
|---|---|---|
| プログラム版（本番） | 画像を使わず、粒・板・線で描く | `fx-smash-fire.js`・`fx-smash-thunder.js`・`fx-smash-charge.js` |
| 画像素材版 | 生成した質感の画像（`effect-assets/`）を使う。takumi 作 | `fire-effects.js`・`thunder-effects.js`・`charge-effects.js` |
| いつもの | 最初からある組 | `effects.js` の中 |

画像素材版とプログラム版は、同じ手本で作っている（炎 小 PK ファイアー・中 ファイガ・大 爆炎、雷 小 サンダー・中 エルサンダー・大 かみなり、溜めは体のまわりのリミットチャージと棒の先のスパーク風の球）。同じ欄のボタンで、試合中でなくても A・B の小・中・大と溜めを出せる（ダメージは入らない）。切り替えの口は `effects.js` の `addStyle`・`setStyle` で、プログラム版は `fx-smash.js` がまとめている。

小・中・大はどれも、狙った向きに飛ぶ弾になる。狙いの初期値は「止める直前の棒の先の動き」で、振って止めたときに棒の先が動いていた向きに飛ぶ（胸から見た動きなので、歩いた分は入らない）。設定で「止めたときの棒の向き」「目から棒の先」にも切り替えられる。ボタンやキーで撃つときは棒が動いていないので、棒の向きに飛ぶ。棒の向きは、接続画面の「棒の軸」の設定を使って、センサー班の動作判定と同じ計算で求める。大きいほど弾が太く、当たりやすい。エフェクトは仮のもので、弾の大きさと、プレイヤー名の下に出る「小」「中」「大！」の文字で見分ける。溜めのメーターは、中に入ると黄色、大に入ると赤になる。

## 被弾のライト

弾が当たると、当たられた側のスマホのライトが光る（小 120 ms、中 250 ms、大 500 ms。`game.js` の `TIER`）。ダッシュボードが `{ type: 'flash', slot, ms }` をサーバーに送り、サーバーがそのスロットのスマホに `{ type: 'flash', ms }` を送る。iOS は端末のライトを直接、Android は ARCore のセッション設定（`Config.FlashMode`）で点ける。

## 振動

溜めている間は、溜めている人のスマホが振動し続ける。ダッシュボードが 0.25 秒ごとに `{ type: 'vibrate', slot, kind: 'charge' }` を送り、1 秒届かないとスマホが自分で止まる（PC やネットワークが落ちても振動が残らない）。勝つと勝った人のスマホが 0.4 秒振動、0.3 秒停止を 5 回繰り返す（`kind: 'win'`）。引き分けでは振動しない。`kind: 'off'` で止まる。

## センサーの記録

接続画面の「センサーの記録」で、スマホ A・B の IMU と AR のパケットを `dashboard/recordings/` に 20 秒ぶん保存する（1 行 1 JSON、git には入れない）。溜めの判定を実際の動きで調整するために使う。

## 位置の求め方

- **スマホ A・B のカメラの向きは自動で見分ける**：スマホによって、ARCore のカメラの座標に対する画面の向きが 90° 単位でずれる（上下左右が逆に出る原因になる）。床のタグを見ながら、0°・90°・180°・270° の 4 通りを全部試して、タグに一番合う向きを選ぶ（「3D空間」の右の欄「カメラの向き補正」に、選んだ向きと 4 通りの残差が出る。選んだ残差だけが小さく、他が大きければ合っている）
- **スマホ C の位置は、床のタグの既知の位置から直接求める**：4 枚 16 個の角の位置と画像上の位置から、スマホ C の位置・向きを求める（`extrinsics.js`）。縦画角はタグから決まるときだけ測定値、決まらないときは設定の「スマホ C の縦画角」（既定 40°）を使う
- **「3D の左右を反転」「3D の上下を反転」「剣の左右を逆にする」**は、既定ではすべてオフ。上の自動の見分けで合うはずなので、合わないときだけ使う
- **床のタグの置き方**：ID 0〜3 の 4 枚を、部屋の中心に辺を接して並べ、1 つの大きな正方形にする。上から見て時計回りに、左上が 0、右上が 1、右下が 2、左下が 3。4 枚とも同じ向き（紙の上が部屋の −z 側）に置く。原点は大きな正方形の中心。位置と向きは固定で、測らない（`world.js` の `TAG_PITCH` = 隣のタグの中心までの距離、既定は測った紙の幅 `PRINTED`。紙が接しているので中心間は紙の幅になる。`?pitch=` で変えられる）。紙の向きも決まっているので、スマホ A・B は 1 枚が見えるだけで位置が決まる。胸のスマホは、これが画角に入るよう少し下に向ける
- **タグの大きさ**：印刷して切った紙の一辺を定規で測り、`world.js` の `PRINTED` に書く（いまは AprilTag 180 mm。プリンターが縮めるので、200 mm のつもりでもこうなった。RuneTag の魔法陣は下の「倍率」）。他の大きさはすべてここから決まる。AprilTag は一辺の 1/10 の白い余白が四辺にあり、距離を測る黒い四角は紙の 0.8 倍（いまは 144 mm）。アプリは黒い四角を 160 mm（RuneTag は仮想の正方形を 224 mm）と仮定して距離を送るので、ダッシュボードが「本当の大きさ / 仮定した大きさ」倍に直す（`tagScale`）。タグの絵は、紙の大きさ（黒い四角 × 10/8）で描く。胸のスマホにタグは付けない（ID は何でもよく、ID 0〜3 以外は、見つけた場所に固定のタグとして表示される）
- **距離の補正**：以前は固定で 1/1.12 倍していた（タグまで 1.00 m で 1.12 m と測れたため）。これは 180 mm に縮んで印刷された AprilTag の分（144 / 160 = 1/1.11）だったので、`PRINTED` からの補正に置き換えた。同じ 1/1.12 が RuneTag にもかかり、距離が 9% 短く出ていた（RuneTag で位置が合わなかった原因の一つ）
- **棒の軸**：IMU の +Y が棒の先端の向き。接続画面で合わせる必要はない。Calibrate は、そのとき棒が向いていた向きを「正面」にする
- **RuneTag に切り替える**：接続画面の「床のマーカー」で AprilTag / RuneTag を選ぶ（全体の設定。サーバーが `dashboard/settings.json` に保存し、`/marker.js` で全ページに、`welcome` / `marker` でスマホ A・B のアプリに送る。開いているページは読み直す。起動時に `MARKER=rune` でも選べる）。RuneTag は床の魔法陣の 7 枚（ID 0〜6）だけで、胸のタグ 8〜11 や他の配置は AprilTag のまま
  - 印刷：`mahoujin/magic-circle-576808920-A3.pdf`（A3 33 ページの組み立てキット。1〜2 ページに貼り方と寸法）。設計では直径約 1.4 m、タグ T0〜T6 の中心は魔法陣の中心から半径 490.5 mm の円の上、T0 が 12 時で時計回りに 1/7 周ずつ。床に置くときは T0（紙の上）を A のスタート位置の側（−x、カメラから見て左）に向ける。原点は魔法陣の中心
  - 倍率：接続画面の「魔法陣の倍率（実物 / 設計）」（`settings.json` の `runeScale`、起動時に `RUNE_SCALE=` でも）。PDF の 100 mm が 97.5 mm に印刷されたので既定は 0.975。タグの大きさと配置の円の両方にかかる。スマホ A・B は設計の大きさで距離を送り、ダッシュボードが倍率をかける（`tagScale`）。倍率を変えると保存したスキャンは使われなくなるので、スキャンし直す
  - しくみ：タグは本物の RUNE-Tag（RUNE-43、IDX 8・10・15・23・24・26・29）。43 区画 × 3 重の黒い点（127.82 mm の 4/6・5/6・6/6、点の半径は層の半径 / 17.8）。符号（`RUNE_CODES`）はキットの 27〜33 ページから読み取ったもので、どの 2 つ（ID と回転）も 129 bit 中 45 bit 以上違う。検出器は自作（`dashboard/public/runetag.js`、アプリは同じ処理の移植 `Rune.kt` / `Rune.swift`）で、点の並びからホモグラフィーを求め、パッチの円（Ø 280 mm）の 0.8 倍（設計上 224 mm）の「仮想の正方形」の 4 隅として返す。以降の計算（スキャン、スマホの位置合わせ、3D 表示）は AprilTag と同じ
  - 見え方の限界（合成画像のテスト `dashboard/test-rune.mjs`）：RUNE-43 の点は小さい（外側の点 Ø 14 mm、隣と 4 mm）ので、パッチが画像で約 110 px より小さいと読めない（前の 18 区画の自作マーカーより届く距離が短い）。スマホ C（1080p、縦画角 40°）は 2.5 m で 7 枚とも読めて姿勢の誤差 1 mm、3.5 m では 7 枚中 3 枚、4.5 m では 0 枚

- **スマホ A・B**：アプリが送る重力基準の ARCore の姿勢（`wp`/`wq`）を、そのスマホが見たフィールドのタグで「向き1つと位置」だけ合わせてフィールドの座標に置く（`phonealign.js`）。偽スマホのシミュレーターでは最大誤差 1cm 未満。胸にタグは付けない（相手の位置は、相手のスマホの ARCore で分かる）
- **スマホ C**：スキャンで求めたカメラの位置・向き・画角（`fieldmap.js`）。最終映像はこのカメラから 3D を描いて重ねる
- **剣**：手の位置（胸の位置 + 手のずれ）+ IMU の向き × 棒の長さ
- **プレイヤーの位置の取り方**（設定）：自動（胸スマホが合っていればそれ、なければ直前の位置）、胸スマホ、立ち位置

## 元のフォルダとの関係

`kawashima/` と `sensing/` のモジュール（`world.js`、`phonealign.js`、`effects.js`、`field3d.js`、`drone.js`、`fieldmap.js`、`extrinsics.js`、`audio.js`、`camlink.js`、`map.js`、`actions.js` など）は `dashboard/public/` にコピーして使っている。変えたのは、ポートの決め打ち（8000/8002/8443 → 同じポート）だけ。`fake-world.mjs` は、本物のアプリと同じく `wp`/`wq` とカメラの内部パラメータも送るようにした。新しく書いたのは `vision.js`、`visionfx.js`、`server.mjs`、`index.html`、`app.js`、`hub.js`、`video.js`、`game.js`、`stage.js`、`space3d.js`、`connect.js`。
